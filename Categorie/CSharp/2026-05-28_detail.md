# CSharp / .NET — Détail du jeudi 28 mai 2026

## 1. .NET 11 Preview 4 — Runtime async stable, JIT plus agressif, JSON first-class dans EF Core

**Source :** Microsoft DevBlog — https://devblogs.microsoft.com/dotnet/dotnet-11-preview-4/
**Date :** 12 mai 2026

### Contexte

.NET 11 (non-LTS) est attendu en **novembre 2026**, dans la cadence annuelle classique de Microsoft. La Preview 4 du 12 mai marque une étape importante : c'est la première où **Runtime Async** — réécriture native du modèle async/await dans le runtime, plus besoin de générer une state machine côté compilateur — n'exige plus le flag `EnablePreviewFeatures=true` pour les projets `net11.0`. Tu peux donc commencer à l'utiliser en POC sans flag de feature.

### Ce qui change concrètement

**Runtime Async généralisé** — Stack traces plus propres (les méthodes async apparaissent dans leur ordre logique, plus l'enchevêtrement habituel avec les types de continuation), overhead allocations réduit (suppression d'une allocation par `await` dans le hot path), et perf JIT améliorée car le runtime gère lui-même la suspension.

**JIT — nouvelles optimisations** — Bounds check elimination plus agressive, removal des redondants `checked` context, switch expression folding (les `switch` sur des constantes sont aplatis), constant-folding de `SequenceEqual`, et redundant branch elimination. Concrètement : entre 2 et 8% de gains sur les benchmarks micro selon les workloads.

**Arm SVE2 intrinsics** — Nouveaux `ShiftRightLogicalNarrowingSaturate(Even|Odd)`. Pertinent si tu déploies sur Graviton4 (AWS), Cobalt 100 (Azure) ou Apple Silicon — toutes les puces récentes Arm exposent SVE2.

**EF Core : JSON columns first-class** — Les colonnes JSON sont désormais représentées dans le modèle relationnel avec une structure de path navigable. Les queries LINQ qui traversent un sous-document JSON sont traduites en SQL natif (`JSON_VALUE`, `JSON_QUERY` selon le provider).

**Templates mcpserver bundled** — Le SDK .NET 11 contient maintenant un template `dotnet new mcpserver` sans installation séparée. Le scaffolding produit un serveur MCP fonctionnel en C# en 5 minutes.

### Pourquoi ça compte pour toi

Si tu fais du .NET en production et que tu pousses du code async-heavy (API HTTP, Functions, services SignalR), Runtime Async vaut le coup d'œil sur la Preview 4 — les traces propres seules valent l'investissement temps. Pour la prod, attends la GA en novembre. Côté EF Core, le support JSON natif règle un cas d'usage récurrent (logs structurés, configurations dynamiques, blobs de métadonnées) qu'il fallait sinon traiter en raw SQL ou via JsonDocument.

### Détails techniques

**Span-based compression** — Nouvelles APIs `Deflate`/`ZLib`/`GZip` qui acceptent `ReadOnlySpan<byte>` et `Span<byte>` sans allocation intermédiaire. Pertinent pour les services de logging/observability qui compressent à la volée.

**Floating-point hex formatting** — Format `"X"` pour les `float`/`double`, utile pour les sérialisations exactes (round-trip lossless).

**.NET MAUI sur CoreCLR par défaut** — Mono est en sortie progressive. Gain de perf substantiel sur Android (de l'ordre de 20-30% sur les cold starts d'apps complexes).

## 2. Improving C# Memory Safety — Le `unsafe` keyword devient explicite (C# 16)

**Source :** Microsoft DevBlog — https://devblogs.microsoft.com/dotnet/improving-csharp-memory-safety/
**Date :** 21 mai 2026

### Contexte

Le débat « C# devrait-il devenir memory-safe comme Rust ? » revient régulièrement depuis que Microsoft a annoncé ses efforts memory safety sur l'ensemble de la stack Windows. La position prise par Richard Lander (PM .NET) est claire : pas question de transformer C# en Rust, mais **rendre explicite et auditable tout code qui peut violer la safety**. La proposition, qui sera C# 16 (en preview .NET 11, GA .NET 12), redéfinit le périmètre du keyword `unsafe`.

### Ce qui change concrètement

**Nouveau périmètre de `unsafe`** — Aujourd'hui, `unsafe` ne s'applique qu'aux pointeurs (`int*`, `&x`). Demain, il englobera toute opération que le compilateur ne peut pas prouver safe : appels à du P/Invoke non annoté, accès `Marshal.Read*`, `MemoryMarshal.CreateSpan`, etc.

**Commentaires de safety obligatoires** — Chaque utilisation de `unsafe` devra être documentée via un nouveau style de commentaire qui décrit les obligations du caller (« le pointer doit pointer vers une zone d'au moins N octets allouée », etc.). Inspiré directement de la convention Rust `// SAFETY: ...`.

**Migration assistée** — Microsoft livrera un `dotnet format` fixer qui wrappe automatiquement les appels unsafe existants dans des blocs `unsafe { }`, déplace le modifier `unsafe` des types vers leurs membres, etc.

### Pourquoi ça compte pour toi

Si tu fais du code interop, du parsing binaire, ou des appels P/Invoke, **prépare ta codebase à expliciter les unsafe**. Concrètement : lance le fixer en preview dès la sortie de .NET 11, puis ajoute les commentaires SAFETY au fil de l'eau dans tes PRs. C'est une vraie amélioration en revue de code — tu vois immédiatement les contrats que chaque appel impose, et tu peux les vérifier (ou les casser sciemment) en connaissance de cause.

### Points de vigilance

**Opt-in initial** — Le nouveau modèle sera opt-in en .NET 11/12, puis vraisemblablement default en .NET 13 (LTS). Tu as ~18 mois pour préparer ta codebase. Les libs tierces (notamment celles à fort niveau d'interop : SkiaSharp, ImageSharp, Npgsql) devront migrer également — surveille leurs roadmap.

**Pas une garantie de memory safety** — La proposition rend les unsafe **visibles**, elle ne les **élimine** pas. Pour de vraies garanties au niveau Rust, il faudrait borrow checking, ce qui n'est pas envisagé pour C#.

## 3. Agent Governance Toolkit MCP Extensions for .NET

**Source :** Microsoft DevBlog — https://devblogs.microsoft.com/dotnet/announcing-agent-governance-toolkit-mcp-extensions-for-dotnet/
**Date :** 21 mai 2026

### Contexte

Microsoft annonce un package officiel `Microsoft.Extensions.Agents.Governance` qui ajoute une couche de **gouvernance, observabilité et policy enforcement** au-dessus des serveurs MCP construits en .NET. C'est la réponse au constat que de plus en plus d'agents tournent en production sans audit trail, sans contrôle de débit, sans validation des outputs.

### Ce qui change concrètement

**Policy engine déclaratif** — Tu définis des règles en YAML ou en code (allow-list de tools, quotas par tenant, validation de schemas d'output, redaction automatique de PII). Les règles sont évaluées à l'invocation de chaque outil MCP.

**Audit trail OpenTelemetry** — Toutes les invocations d'outils, leurs inputs, outputs et durées sont émis comme spans OpenTelemetry. Compatible avec Azure Monitor, Datadog, Honeycomb.

**Rate limiting et circuit breaking intégrés** — Plus besoin d'écrire ces middlewares à la main. Configuration en quelques lignes pour limiter un agent à N appels/minute par utilisateur.

### Pourquoi ça compte pour toi

Si tu construis un assistant interne ou un produit avec une couche agent en .NET, **ce package te fait gagner plusieurs sprints**. La gouvernance des agents est un sujet sous-traité aujourd'hui — chacun bricole sa solution. Avoir un standard Microsoft permet d'aligner les pratiques. Pour intégrer : `dotnet add package Microsoft.Extensions.Agents.Governance` puis injecter `AddAgentGovernance()` dans ton `IServiceCollection`.

## 4. NuGet Package Pruning — Dépendances plus propres, vulnérabilités actionnables

**Source :** Microsoft DevBlog — https://devblogs.microsoft.com/dotnet/nuget-package-pruning-in-dotnet-10/
**Date :** 18 mai 2026

### Contexte

Les graphes de dépendances NuGet ont tendance à enfler silencieusement (transitive dependencies, packages métapackage qui tirent 30 sous-packages). Microsoft livre dans le SDK .NET 10/11 une fonctionnalité de **pruning** qui exclut automatiquement des dépendances que ton projet n'utilise pas réellement, et améliore la lisibilité des reports de vulnérabilités.

### Ce qui change concrètement

**`<PrunePackageReference>`** — Nouvelle directive dans `.csproj`. Tu listes les packages que ton projet ne consomme pas directement (par exemple, NuGet auto-référencé par un metapackage). Le build les exclut du graphe résolu.

**Reports CVE actionnables** — `dotnet list package --vulnerable` indique désormais quelle dépendance directe est responsable de tirer une transitive vulnérable. Plus de chasse au cœur de l'arbre.

**Auto-pruning intelligent** — Le SDK détecte automatiquement les packages référencés par des metapackages que ton code ne consomme pas réellement, et propose un PR-ready `dotnet pack --prune-suggestions`.

### Pourquoi ça compte pour toi

Tes builds peuvent gagner plusieurs centaines de Mo et plusieurs secondes en `dotnet restore`. Surtout : tu réduis ta surface d'attaque (moins de packages = moins de CVE potentielles). Pour démarrer : `dotnet list package --vulnerable` sur tes solutions critiques, identifie les CVE remontées, et utilise les nouveaux outils pour décider si tu purges ou si tu update.
