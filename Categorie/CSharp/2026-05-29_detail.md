## 1. EF Core 11 Preview 4 — Vector search SQL Server 2025, ChangeTracker plus malin, JSON first-class

**Source :** Microsoft .NET Blog — https://devblogs.microsoft.com/dotnet/dotnet-11-preview-4/
**Date :** 12 mai 2026

### Contexte

EF Core 10 (LTS, novembre 2025) avait déjà introduit le support du vector search côté providers, mais la traduction SQL générique restait limitée. La Preview 4 de `.NET 11` est la première à transformer ces APIs en quelque chose d'utilisable end-to-end avec **SQL Server 2025**, qui expose maintenant les types `VECTOR` et les fonctions `VECTOR_DISTANCE` côté moteur. En parallèle, EF Core continue de répondre à des demandes anciennes : moins de friction sur les colonnes JSON, et un `ChangeTracker` qui ne te force plus à passer par `DetectChanges()` quand tu sais déjà ce que tu cherches.

### Ce qui change concrètement

- **Vector search natif SQL Server 2025** : `VectorSearch(target, distance)` retourne les lignes triées par distance vectorielle. `WithApproximate()` instruit le moteur d'utiliser un index vectoriel (HNSW côté SQL Server) plutôt qu'un scan exact. Traduction LINQ complète : `query.OrderBy(p => EF.Functions.VectorDistance(p.Embedding, target)).Take(10)`.
- **`ChangeTracker.GetEntriesForState()`** : retourne `IEnumerable<EntityEntry>` filtré par `EntityState` **sans déclencher `DetectChanges()`**. Gain net sur les contextes long-vivants (services BG, agents IA, pipelines de streaming) où un `DetectChanges()` à chaque tick devient le bottleneck.
- **JSON columns first-class** : représentation structurée des chemins JSON dans le modèle relationnel. Concrètement : meilleur diagnostic des requêtes, SQL de partial-update plus propre, comportement cohérent en migrations et compiled models.
- **`ExcludeForeignKeyFromMigrations(true)`** : sort une foreign key du tracking de migrations — pratique pour les bases partagées où la FK est gérée hors EF Core.
- **`.config/dotnet-ef.json`** : `dotnet ef` lit ses options par défaut depuis ce fichier, discovery en remontant depuis le répertoire courant. Plus de copier-coller `--project --startup-project` partout.
- **Temporal tables** : `PeriodStart` / `PeriodEnd` peuvent maintenant être des propriétés CLR normales (plus obligées en shadow).

### Pourquoi ça compte pour toi

Si tu fais du RAG ou de la recherche sémantique avec ton stack `.NET` + SQL Server, tu peux maintenant **garder ton ORM** au lieu de basculer sur du Dapper / SQL brut pour la partie vectorielle. Le `GetEntriesForState()` te débloque sur tes workers EF Core long-vivants où `DetectChanges()` coûtait cher. Et pour tes migrations Symfony-style sur PostgreSQL multi-app, l'exclusion FK règle un irritant historique.

### Points de vigilance

`VectorSearch()` ne tombe back à un scan exact que si l'index vectoriel n'existe pas — vérifie tes plans avant de pousser en prod. La représentation structurée des chemins JSON peut casser des compiled models existants : `dotnet ef migrations script` à comparer avant l'upgrade.

## 2. ASP.NET Core 11 Preview 4 — Blazor Virtualize stable, Web Worker, Aspire service defaults, mcpserver template

**Source :** Microsoft .NET Blog — https://devblogs.microsoft.com/dotnet/dotnet-11-preview-4/
**Date :** 12 mai 2026

### Contexte

La Preview 4 d'ASP.NET Core resserre plusieurs sujets qui traînaient. Blazor a deux corrections d'UX historiques (saut du Virtualize, friction du Web Worker). Le wiring Aspire continue son chemin vers le « par défaut, ça marche ». Et le serveur MCP, qu'on devait jusqu'ici scaffolder à la main ou via nuget custom, devient un template SDK officiel.

### Ce qui change concrètement

- **`Virtualize` — fini le saut viewport** : quand un item au-dessus du viewport change de taille (ex. images chargées async dans une liste de messages), le composant ne décalait plus visuellement le contenu visible. Nouveau paramètre `AnchorMode` qui pilote le comportement quand des items sont préfixés/suffixés (chat UI, logs en streaming, news feed).
- **Blazor Web Worker** : ancien « .NET Web Worker template » renommé. Ajout d'`InvokeVoidAsync` pour les appels fire-and-forget. Cancellation et timeout supportés à la création **et** à chaque invocation.
- **`blazor-wasm-servicedefaults` template** : scaffolde une lib `ServiceDefaults` côté client Blazor WASM avec OpenTelemetry (logs/metrics/traces via OTLP exporter), service discovery, resilience HTTP standard, le tout intégré Aspire.
- **`mcpserver` template** : `dotnet new mcpserver` scaffolde un serveur MCP minimal, prêt à brancher dans Claude Desktop ou autres clients.
- **HTTP QUERY** : `OpenAPI` reconnaît la méthode HTTP QUERY (RFC draft, safe + idempotent + body) comme opération valide pour les endpoints type search.
- **`dotnet run` interactif** : sans TFM ni device explicite, prompt interactif — confort MAUI / mobile.
- **`dotnet watch` + Aspire** : crash recovery, hot-reload sur changements de project/package references, Ctrl+C clean pour WinForms/WPF.

### Pourquoi ça compte pour toi

Si tu maintiens du Blazor avec listes virtualisées (admin tools, dashboards, monitoring), l'`AnchorMode` te règle un bug d'UX que tu avais sûrement contourné à la main. Le template Aspire `servicedefaults` te fait gagner une demi-journée par nouveau projet sur le câblage observabilité. Et `dotnet new mcpserver` te permet de tester l'exposition de tes services internes comme outils MCP en moins de 10 minutes.

### Limites

`AnchorMode` ne couvre pas tous les patterns scroll (jump-to-bottom programmatique reste à toi). Le serveur MCP scaffold n'a pas encore de templates d'authentification — tout est anonymous local pour l'instant.
