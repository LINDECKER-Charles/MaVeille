# Tech — Détail du mardi 16 juin 2026

## 1. CodeIgniter CVE-2026-48062 — RCE via bypass du contrôle d'upload (CVSS 9.8)

**Source :** Daily CyberSecurity — https://securityonline.info/codeigniter-cve-2026-48062/
**Date :** 15 juin 2026

### Contexte

CodeIgniter est l'un des frameworks PHP les plus déployés. La faille `CVE-2026-48062` (CVSS 9.8) touche sa validation des fichiers uploadés et ouvre la porte à une exécution de code arbitraire. Le rayon d'impact est large vu la base installée.

### Ce qui change concrètement

La règle de validation `ext_in` faisait confiance à l'extension dérivée du **type MIME** plutôt qu'au vrai nom de fichier. Un `shell.php` maquillé en contenu de type GIF passait donc le contrôle.

L'exploitation exige un alignement précis de conditions :

- l'application accepte des uploads utilisateur ;
- elle s'appuie sur `ext_in` pour valider ;
- elle stocke les fichiers sous leur **nom d'origine** dans un dossier public.

L'install par défaut n'expose aucun endpoint d'upload, donc tout le monde n'est pas exposé. Correctif : **CodeIgniter v4.7.3**.

### Pourquoi ça compte pour toi

Tu fais du PHP/Symfony : le motif est universel. Audite tes routes d'upload, ne fais jamais confiance à l'extension MIME, renomme avec un `getRandomName()`, stocke hors webroot et coupe l'exécution de scripts dans les dossiers d'upload. Passe en revue les fichiers déjà déposés.

## 2. Wazuh 5.0 — injection CVSS 10 dans le pipeline d'inventaire (OpenSearch bulk)

**Source :** Daily CyberSecurity — https://securityonline.info/wazuh-cvss-10-vulnerability/
**Date :** 15 juin 2026

### Contexte

Wazuh est un SIEM/XDR open source très répandu. Une faille **CVSS 10** vient d'être documentée avec PoC public, ciblant le pipeline de télémétrie d'inventaire de la branche 5.0.

### Ce qui change concrètement

Le pipeline d'inventaire de Wazuh 5.0 transfère un champ flatbuffer fourni par l'agent (`DataValue.index`) **directement** dans un corps NDJSON `OpenSearch_bulk` sans échappement. Un agent malveillant peut donc injecter des délimiteurs et faire passer des opérations bulk arbitraires, exécutées sous les **credentials admin** du manager (keystore local, rôles all-access par défaut).

Conséquences : suppression arbitraire de documents, falsification d'alertes, payloads persistants dans les dashboards — autrement dit destruction de preuves forensiques pendant un incident.

- Versions affectées : `wazuh-manager` ≥ `5.0.0-beta1`.
- Branches 4.x : **non concernées** (le chemin de sync d'inventaire n'existe pas).
- Correctif : **5.0.0-beta3** (échappement correct). Advisory `GHSA-ff9g-85jq-r3g3`.

### Pourquoi ça compte pour toi

Si tu testes Wazuh 5.0 beta sur un lab ou un POC, monte tout de suite en `5.0.0-beta3` avant de brancher des agents non maîtrisés. Ta prod en 4.x reste sûre sur ce point : pas d'urgence de migration vers la 5.0 motivée par ce CVE.

## 3. Apple Container 1.0.0 — VM Linux légères natives sur Apple Silicon

**Source :** Daily CyberSecurity — https://securityonline.info/apple-container-1-0-apple-silicon-linux-vms/
**Date :** 13 juin 2026

### Contexte

Apple a publié sur GitHub (`apple/container`) la version **1.0.0** de son outil CLI open source écrit en Swift, présenté en preview à la WWDC 2025. Objectif : exécuter des conteneurs Linux nativement sur les Mac Apple Silicon.

### Ce qui change concrètement

Le modèle d'isolation tranche avec Docker Desktop : au lieu d'une grosse VM Linux partagée, **chaque conteneur tourne dans sa propre micro-VM** (paquet Swift `Containerization`), avec montage minimal des données hôte. L'outil est compatible **OCI** (pull/build/push vers des registries standard).

Quatre apports en 1.0 :

- **persistance d'état** d'une « Container Machine » (stop/restart en conservant le filesystem) ;
- configuration en **TOML** (fini les system properties) ;
- **copie de fichiers** hôte ↔ conteneur ;
- **sortie structurée** pour l'automatisation (CI/CD).

Prérequis : Apple Silicon, idéalement **macOS 26 Tahoe** (macOS 27 et +). Sur macOS 15 Sequoia, fonctionnalités limitées (pas de réseau inter-conteneurs, gestion mémoire imparfaite).

### Pourquoi ça compte pour toi

Si tu développes sur Mac, c'est une alternative crédible à Docker Desktop : meilleure isolation par conteneur et perfs natives Apple Silicon. Évalue-la sur un service jetable, mais garde en tête les limites mémoire actuelles avant d'y lancer plusieurs conteneurs lourds en continu.

## 4. Linux Kernel 7.1 — stabilité, nouveau driver NTFS, AMD Zen 6

**Source :** Daily CyberSecurity — https://securityonline.info/linux-kernel-7-1-release/
**Date :** 15 juin 2026

### Contexte

Le noyau **Linux 7.1** est sorti : c'est la première mise à jour mineure de la série 7.x, centrée sur la stabilité et la correction de drivers récalcitrants plutôt que sur de grosses nouveautés.

### Ce qui change concrètement

- Correctifs drivers display, réseau et audio ; corrections mémoire et synchronisation d'horloge.
- **Nouveau driver NTFS kernel-level** : meilleure compatibilité et perfs sur partitions Windows.
- Support **préliminaire AMD Zen 6**, optimisations Intel récentes, compatibilité RISC-V élargie.
- Politique de divulgation de sécurité revue pour absorber l'**afflux de rapports de bugs générés par IA**.
- Raffinements file systems, power management et **Landlock**.

Calendrier : la merge window de 7.2 ouvre bientôt, **RC1 le 28 juin**, sortie 7.2 visée fin août.

### Pourquoi ça compte pour toi

Côté desktop, l'upgrade 7.0.x → 7.1 est sans histoire. Côté serveurs (PostgreSQL, conteneurs), tu valides en staging avant la prod : valide surtout les drivers réseau et le comportement Landlock. Si tu provisionnes du matériel Zen 6 ou RISC-V, 7.1 améliore la prise en charge mais attends la 7.2 pour de la prod sereine.
