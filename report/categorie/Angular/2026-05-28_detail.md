# Angular — Détail du jeudi 28 mai 2026

## 1. Angular 22 passe en stable — MCP intégré dans l'outillage officiel

**Source :** FrontendMinds / Angular blog — https://frontendminds.com/blog/angular-latest-version-2026
**Date :** 20 mai 2026 (release stable)

### Contexte

Le digest d'hier couvrait la **RC1 d'Angular 22** sortie le 22 mai. En réalité, l'équipe Angular a tagué la **release stable dès le 20 mai 2026**, et plusieurs analyses détaillées publiées cette semaine (FrontendMinds, HeroDevs, VersionLog) confirment le périmètre final. La nouveauté la plus structurante pour ton workflow quotidien n'est pas dans les features de framework déjà connues (Signal Forms, zoneless par défaut, Selectorless Components) mais dans **l'intégration native du Model Context Protocol (MCP) dans l'outillage officiel Angular** — un signal très clair sur la stratégie de l'équipe vis-à-vis des assistants de code.

### Ce qui change concrètement

**MCP support stable dans Angular CLI** — Angular 22 ship un serveur MCP officiel installable via `ng add @angular/mcp`. Une fois activé, ton IDE (Cursor, Claude Code, Copilot, Cline) peut interroger l'arbre de composants, demander une migration assistée vers les signals, ou générer du code avec une connaissance exacte de la version du projet. Concrètement : le LLM ne te propose plus du code Angular 12 quand tu es sur la 22.

**Signal Forms stables** — Aucun breaking change vs la RC, mais les guides de migration des Reactive Forms ont été publiés. La conversion mécanique se fait via `ng generate @angular/forms:signal-form-migration --path src/app/...`.

**Selectorless Components production-ready** — La syntaxe `<UserCard [user]="..."/>` (sans déclaration de selector) est désormais le pattern recommandé pour les nouveaux composants. Les linters et le Language Service reconnaissent l'import direct.

**Vitest comme runner par défaut** — Pour les nouveaux projets `ng new`. Karma reste supporté mais en mode maintenance. Vitest apporte un démarrage 2-3× plus rapide sur les gros monorepos.

### Pourquoi ça compte pour toi

Si tu n'avais pas encore prévu la bascule en stable (tu attendais la fin du cycle RC), c'est le moment d'inscrire la migration au planning. Pour les projets sous Angular 19-21, le path de migration est balisé. **Installe surtout le serveur MCP** dans ton workflow : `ng add @angular/mcp` puis configure ton client (Cursor / Claude Code) pour pointer vers `http://localhost:<port>/mcp`. Tu vas immédiatement constater une qualité accrue des suggestions de code Angular dans ton IDE.

### Points de vigilance

**Angular 21 reste LTS jusqu'à mai 2027** — Pas d'urgence existentielle pour migrer, surtout sur des projets en maintenance. Mais Angular 21 ne reçoit plus que des fixes de sécurité.

**Outillage tiers** — Les libs comme Nx, NgRx, Spartan, PrimeNG ont publié leurs versions compatibles v22 cette semaine. Vérifie le tableau de compatibilité avant de bumper en blind.

## 2. Newsletter Angular hebdo — Dynamic Components, HTTP Resources, AI Writing

**Source :** Angular Blog (Medium) — https://blog.angular.dev/mastering-dynamic-components-http-resources-and-ai-writing-assistants-%EF%B8%8F-94c18a911a3a
**Date :** 22 mai 2026

### Contexte

La newsletter hebdomadaire officielle synthétise les contenus communautaires retenus par l'équipe Angular. Cette édition met l'accent sur trois axes qui complètent bien la sortie d'Angular 22 : la manipulation programmatique des composants dynamiques, les `HttpResource` (alternative signal-first aux `HttpClient.get().subscribe()`), et l'intégration d'assistants AI dans l'écriture de templates.

### Ce qui change concrètement

**Dynamic Components revisités** — La nouvelle API `createComponent()` couplée à `viewChild()` rend la création de composants imbriqués déclaratifs (modals, drawers, dynamically loaded widgets) bien plus simple. Plus besoin de manipuler `ComponentFactoryResolver` (déprécié depuis longtemps mais souvent encore présent dans le code legacy).

**HttpResource** — Remplaçant signal-first du couple `HttpClient` + `subscribe`. Un `HttpResource` expose un signal `value()`, un signal `status()` (loading/error/success), et se recharge automatiquement quand ses dépendances signal changent. Réduit drastiquement la quantité de code dans les composants smart.

**AI Writing Assistants** — Plusieurs articles décrivent comment configurer Copilot, Claude Code et Cursor pour produire du code Angular idiomatique — notamment en injectant les directives officielles d'Angular dans le contexte (`AGENTS.md` à la racine du projet, ou MCP server officiel).

### Pourquoi ça compte pour toi

C'est le pattern signal-first appliqué partout : les `HttpResource` éliminent un pan entier de boilerplate (gestion des `Subscription`, `takeUntilDestroyed`, `BehaviorSubject` intermédiaires). Si tu lances un nouveau projet ou refactores une vue, c'est le pattern à privilégier. Pour Dynamic Components, la nouvelle API mérite d'être adoptée même sur du code existant — elle est plus testable et lisible.

### Limites

**HttpResource ne remplace pas tous les cas** — Pour les flux complexes (websockets, retry avec backoff exponentiel, combinaisons de plusieurs streams), RxJS reste plus expressif. `toSignal()` et `toObservable()` permettent de cohabiter.
