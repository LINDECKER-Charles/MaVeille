# Angular — Détail du samedi 26 septembre 2026

## 1. scriptc (Vercel Labs) — compiler du TypeScript en binaire natif, sans moteur JS

**Source :** InfoQ — https://www.infoq.com/news/2026/09/vercel-scriptc-node/
**Date :** 25 septembre 2026

### Contexte

Node.js domine le runtime JS/TS depuis quinze ans, mais son démarrage — V8, libuv, le chargement des modules — coûte cher en cold start, surtout pour les CLI et les fonctions serverless. Bun et Deno ont réduit ce coût sans changer de paradigme : ils embarquent toujours un moteur JavaScript complet. Vercel Labs, l'équipe derrière Turbopack, part d'un postulat différent avec scriptc : et si le TypeScript strictement typé n'avait plus besoin d'un moteur JS du tout ?

Le projet, publié sous licence Apache 2.0, cible les CLI, les scripts d'infra et les petits services HTTP où la latence de démarrage et l'empreinte mémoire comptent plus que l'accès à l'écosystème npm complet. Ce n'est pas un concurrent direct de Node pour une appli Angular — plutôt un outil pour l'outillage qui gravite autour (CLI internes, scripts de build, tooling Nx).

### Comment ça marche

scriptc réutilise le compilateur TypeScript officiel (`tsc`) pour le parsing et le type-checking : pas de réimplémentation du système de types. Une fois le programme validé, il est abaissé vers une représentation intermédiaire (IR) typée, comme le ferait un compilateur AOT classique. Cette IR peut ensuite être émise vers plusieurs cibles : C, LLVM IR, assembleur, objets natifs, exécutables natifs, ou WebAssembly via WASI Preview 1.

Le point clé, c'est la gestion de trois profils d'exécution. Le code purement statique — types connus à la compilation, formes d'objets fixes — est compilé directement en code machine. Le code qui a besoin de dynamisme (`eval`, objets à forme variable, la plupart des packages npm classiques) peut tourner dans un moteur `quickjs-ng` embarqué (~620 Ko) via le flag `--dynamic`. Et tout le reste — une construction que le compilateur ne sait pas prouver statiquement sans ce flag — est rejeté dès la compilation, avec un message qui indique où ça bloque.

La mémoire est gérée par comptage de références plutôt que par un GC générationnel façon V8, ce qui explique le démarrage en 1,78 ms et une empreinte idle de 1,9 Mio pour un serveur HTTP sans framework.

```mermaid
flowchart LR
  A[Source .ts] --> B[tsc : parse + typecheck]
  B --> C[IR typée]
  C --> D{Dynamisme requis ?}
  D -- non --> E[Code natif : C / LLVM / asm]
  D -- oui, avec --dynamic --> F[Moteur quickjs-ng ~620 Ko]
  D -- oui, sans --dynamic --> G[Rejeté à la compilation]
  E --> H[Binaire natif autonome]
  F --> H
```

### En pratique — exemple de code

```typescript
// server.ts — code identique pour Node et scriptc
import { createServer } from "node:http";

const server = createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain" });
  res.end("ready\n");
});

server.listen(3000);
```

```bash
# Avant — Node : moteur V8 complet embarqué, ~62 ms de démarrage
node server.ts

# Après — scriptc : compilation AOT vers binaire natif autonome
scriptc build server.ts -o server-native
./server-native   # ~1.8 ms de démarrage, 1.9 Mio idle
```

### Pourquoi ça compte pour toi

Si tu écris des CLI internes ou des Cloud Functions autour de ton appli Angular, ça change le calcul coût/latence : un cold start dix fois plus rapide qu'avec Bun, sans réécrire en Go ou Rust. Mais la contrainte est réelle — la plupart des packages npm utilisent du dynamisme que scriptc doit alors exécuter dans quickjs-ng, avec un coût CPU non négligeable. À réserver, pour l'instant, aux scripts où tu maîtrises tout le code, pas à une appli Angular complète.

### Pour aller plus loin

scriptc reste expérimental (v0.0.16), pas encore recommandé en prod. À surveiller si tu maintiens de l'outillage CLI dans un monorepo Angular/Nx — c'est typiquement le genre de code statique et sans dépendances exotiques où l'approche brille.
