# Angular — Synthèse du lundi 7 septembre 2026

## Digest court

Deux angles aujourd'hui, tous les deux sur la même idée : déplacer la complexité hors du composant. Côté framework, `22.2.0-next.5` et `22.1.5` corrigent une fuite de timers dans `debounced()`, la primitive de debounce signal-native introduite avec Angular 22 — l'occasion de comprendre pourquoi elle renvoie une `Resource` et pas un simple signal. Côté architecture, Airbnb publie le bilan de son passage à une authentification pilotée par le serveur : 60 % de code d'auth en moins, 100 Ko de bundle web économisés, et un taux de succès en hausse de 2,6 %. Le pattern est directement transposable à une app Angular adossée à une API .NET ou Symfony. Journée calme côté releases majeures — le blog Angular n'a rien publié depuis le 2 septembre.

## Top 1 — `debounced()` : la fuite de timers corrigée

- **`22.2.0-next.5` / `22.1.5`** : les timers de debounce périmés sont désormais annulés, plus de fuite quand la source change vite.
- **Signal in, Resource out** : `debounced()` expose `value()`, `status()`, `isLoading()` et `error()` — l'état d'attente devient observable.
- **Sans RxJS** : plus besoin de `debounceTime` + `switchMap` pour un simple champ de recherche piloté par signaux.

## Top 2 — Airbnb : l'authentification pilotée par le serveur

- **-60 % de code d'auth** et **-100 Ko** sur le bundle web, à iso-fonctionnalité.
- **+2,6 % d'authentifications réussies**, **-27 % de comptes dupliqués**, **-11 % de coûts OTP**.
- **Le client devient un moteur de rendu** : c'est le serveur qui choisit le challenge (mot de passe, OTP, passkey) selon la politique.

Le point commun des deux sujets : dans les deux cas, le client arrête de porter une machine à états qu'il gère mal — un timer dans un cas, un arbre de décision d'auth dans l'autre.
