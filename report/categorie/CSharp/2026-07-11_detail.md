## 1. EF Core 10 — filtres de requête nommés (multi-tenant + soft-delete enfin cumulables)

**Source :** Microsoft Learn — https://learn.microsoft.com/en-us/ef/core/what-is-new/ef-core-10.0/whatsnew
**Date :** EF Core 10 (LTS, novembre 2025 — toujours d'actualité)

### Contexte

Depuis des années, EF Core n'autorise qu'**un seul filtre global par type d'entité**. Chaque appel à `HasQueryFilter` **écrase** le précédent. Résultat : dès que tu veux cumuler deux règles transverses — typiquement un *soft-delete* (`IsDeleted == false`) **et** une isolation *multi-tenant* (`TenantId == current`) — tu es obligé de les fusionner à la main dans une seule expression. Et le jour où tu veux en désactiver une seule (par exemple pour un écran d'administration qui doit voir les lignes supprimées), `IgnoreQueryFilters()` les enlève **toutes**, y compris l'isolation tenant. C'est un piège de sécurité classique.

### Comment ça marche

EF Core 10 introduit les **filtres nommés**. Tu peux déclarer plusieurs `HasQueryFilter` sur la même entité, chacun identifié par une clé string. À la lecture, EF les combine tous en `AND`. Surtout, `IgnoreQueryFilters` accepte désormais une liste de noms : tu désactives **chirurgicalement** le filtre voulu et tu gardes les autres actifs. Le mécanisme se pose au niveau du modèle (`OnModelCreating`), donc il s'applique automatiquement à **toutes** les requêtes sur l'entité — `Find`, navigation, `Include`, projections — sans que tu penses à le réappliquer.

### En pratique — exemple de code

```csharp
// Avant — EF Core 9 : un seul filtre, tout fusionné, tout ou rien
modelBuilder.Entity<Invoice>()
    .HasQueryFilter(i => !i.IsDeleted && i.TenantId == _tenant.Current);

// IgnoreQueryFilters() enlève AUSSI l'isolation tenant -> fuite de données possible
var all = db.Invoices.IgnoreQueryFilters().ToList();

// Après — EF Core 10 : deux filtres nommés, indépendants
modelBuilder.Entity<Invoice>()
    .HasQueryFilter("SoftDelete", i => !i.IsDeleted)
    .HasQueryFilter("Tenant",     i => i.TenantId == _tenant.Current);

// L'admin voit les lignes supprimées MAIS reste borné à son tenant
var deletedForTenant = db.Invoices
    .IgnoreQueryFilters(["SoftDelete"])   // on ne lève QUE le soft-delete
    .Where(i => i.IsDeleted)
    .ToList();
```

### Pourquoi ça compte pour toi

Si tu maintiens une API multi-tenant, tu peux enfin séparer isolation et soft-delete sans requête maison ni risque de tout désactiver d'un coup. Tu réduis la surface d'erreur : lever un filtre technique n'ouvre plus la porte aux données d'un autre client. Migration quasi gratuite — nommer tes filtres existants suffit.

### Points de vigilance

Un filtre non nommé reste possible (rétrocompatible) mais tu ne peux en avoir qu'un seul « anonyme » par entité. Nomme systématiquement pour pouvoir cibler plus tard.

## 2. EF Core 10 — opérateurs `LeftJoin` / `RightJoin` natifs en LINQ

**Source :** heise online — https://www.heise.de/en/news/NET-10-Release-Candidate-1-Follow-up-for-Entity-Framework-Core-10641147.html
**Date :** EF Core 10 / .NET 10 (LTS)

### Contexte

Écrire une **jointure externe** en LINQ a longtemps été pénible. LINQ n'avait pas d'opérateur `LEFT JOIN` : il fallait passer par `GroupJoin`, puis `SelectMany` sur le résultat, puis `DefaultIfEmpty()` pour émettre `null` côté droit quand rien ne correspond. Trois étapes, beaucoup de bruit, et un pattern que la moitié de l'équipe copie-colle sans le comprendre.

### Comment ça marche

.NET 10 ajoute deux vrais opérateurs LINQ, `LeftJoin` et `RightJoin`, disponibles à la fois sur `IEnumerable` (LINQ to Objects) et sur `IQueryable`. Côté EF Core 10, le provider les **traduit directement** en `LEFT JOIN` / `RIGHT JOIN` SQL. Signature : les clés des deux côtés, puis un sélecteur de résultat qui reçoit l'élément de gauche et l'élément de droite (potentiellement `null`). Tu exprimes l'intention (« garde toutes les commandes, associe le client s'il existe ») au lieu de décrire la mécanique.

### En pratique — exemple de code

```csharp
// Avant — le triptyque GroupJoin + SelectMany + DefaultIfEmpty
var q = db.Orders
    .GroupJoin(db.Customers, o => o.CustomerId, c => c.Id,
               (o, cs) => new { o, cs })
    .SelectMany(x => x.cs.DefaultIfEmpty(),
                (x, c) => new { x.o.Id, Customer = c.Name });

// Après — EF Core 10 : un seul opérateur, lisible, même SQL généré
var q = db.Orders.LeftJoin(
    db.Customers,
    o => o.CustomerId,          // clé à gauche
    c => c.Id,                  // clé à droite
    (o, c) => new {             // c peut être null
        o.Id,
        Customer = c != null ? c.Name : "(sans client)"
    });
// SQL : SELECT o.Id, c.Name ... FROM Orders AS o LEFT JOIN Customers AS c ON ...
```

### Pourquoi ça compte pour toi

Tes jointures externes deviennent lisibles au premier coup d'œil, en revue comme six mois plus tard. Le SQL produit reste identique, donc zéro régression de perf : c'est un gain d'ergonomie pur. Sur une base PostgreSQL via Npgsql, la traduction fonctionne pareil. Tu peux nettoyer les vieux `DefaultIfEmpty()` au fil de l'eau.

### Pour aller plus loin

EF Core 10 apporte aussi la **recherche vectorielle** (`VECTOR_DISTANCE`) et le type `json` natif sur SQL Server 2025 / Azure SQL — utile si tu adosses de la similarité sémantique à ta base relationnelle plutôt qu'à un vector store séparé.
