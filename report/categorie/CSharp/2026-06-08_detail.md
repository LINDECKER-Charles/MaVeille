# CSharp — Détail du lundi 8 juin 2026

## 1. EF Core 11 Preview 4 — outillage migrations pour Aspire et conteneurs

**Source :** .NET Blog — https://devblogs.microsoft.com/dotnet/dotnet-11-preview-4/
**Date :** 2 juin 2026

### Contexte

La Preview 4 d'EF Core 11 a déjà fait parler d'elle pour le vector search SQL Server 2025 et le JSON first-class. Mais une partie de la livraison concerne le **flux de migrations** et la **developer experience CLI** — moins spectaculaire, plus quotidien. C'est utile dans les scénarios **Aspire** et **conteneurisés**, où la recompilation à la volée n'est pas toujours possible.

### Ce qui change concrètement

- **`dotnet ef database update --add`** : crée *et* applique une migration en une seule commande. Roslyn compile la migration au runtime, ce qui débloque les environnements sans recompilation (Aspire, conteneurs).
- **Colonnes temporelles** (temporal tables SQL Server) exposables comme **propriétés CLR** ordinaires : tu les lis comme n'importe quelle colonne.
- Plusieurs opérations **`DateTimeOffset`** se traduisent maintenant en SQL côté SQL Server — des requêtes qui échouaient en « could not be translated » passent.
- La CLI `dotnet ef` charge ses valeurs par défaut depuis un fichier **`.config/dotnet-ef.json`**.

### Pourquoi ça compte pour toi

Si tu pilotes tes migrations en CI ou dans des conteneurs, `--add` supprime une étape et fiabilise les déploiements automatisés. Les colonnes temporelles en CLR simplifient l'audit de tes entités sans mapping manuel. Et les traductions `DateTimeOffset` évitent des contournements LINQ pénibles sur PostgreSQL ou SQL Server. Teste sur une branche : c'est une préversion, pas du LTS.

### Points de vigilance

- C'est **.NET 11 Preview 4** : non destiné à la prod, API susceptible de bouger d'ici la GA de novembre 2026.
- Vérifie que ton provider (Npgsql pour PostgreSQL) suit les mêmes traductions ; certaines optimisations ciblent d'abord SQL Server.
