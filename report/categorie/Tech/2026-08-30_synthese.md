# Tech — Synthèse du dimanche 30 août 2026

## Digest court

Une leçon d'humilité et deux primitives d'infrastructure. **JetBrains** a publié le 28 août la post-mortem d'une compromission de son service Cadence : le serveur TeamCity qui l'orchestrait n'avait **jamais été patché** contre CVE-2026-63077, la faille que JetBrains avait elle-même divulguée le 27 juillet et dont elle avait signalé l'exploitation active le 7 août. Seize jours d'accès attaquant, une sauvegarde complète de 2024 exfiltrée, des IAM AWS compromis. Côté plateformes, **Cloudflare Workers accepte enfin des connexions TCP entrantes** après huit ans de restriction à HTTP, avec gRPC comme premier protocole au-dessus — en bêta privée. Et **Uber** décrit GitFarm, qui transforme Git en service gRPC centralisé : checkout complet en moins de 500 ms au lieu de 15 minutes de clonage.

## Top 1 — À traiter : JetBrains Cadence compromis via son propre TeamCity non patché

- **Chronologie** : CVE-2026-63077 divulguée le 27 juillet (RCE non authentifiée, commandes OS avec les privilèges du process TeamCity). Exploitation active annoncée le 7 août. Intrusion sur `api.cadence.jetbrains.com` **à partir du 8 août**, détectée le 23, serveur retiré le 24.
- **Périmètre** : sauvegarde complète du serveur Cadence de 2024 (identifiants, configs, artefacts, logs), **plusieurs utilisateurs IAM AWS compromis**, fichiers lus dans des buckets S3 de JetBrains.
- **Le code source aussi** : le plugin PyCharm synchronisait les fichiers de projet vers Cadence avant exécution.
- **À faire si tu as utilisé Cadence** : traiter comme compromis tout secret passé par le service, y compris les tokens npm, Maven, NuGet, PyPI et les registres de conteneurs — un attaquant avec des droits de publication peut empoisonner la chaîne d'approvisionnement.
- **Ce qui est plus dur** : JetBrains demande de considérer les **exécutions et leurs sorties** comme non fiables. Les artefacts produits doivent être rejoués contre du code source de confiance.

Six adresses IP d'exploitation ont été publiées, explicitement présentées comme **non exhaustives**.

## Top 2 — Cloudflare Workers : `connect(socket)` et TCP entrant

- **Huit ans de contrainte levée** : un Worker pouvait ouvrir des sockets sortantes, mais ne pouvait être serveur que pour HTTP. Le nouveau handler `connect(socket)` accepte une socket brute routée via **Spectrum**.
- **Chaîne complète** : Worker → Durable Object → Container via `getTcpPort()`. Un serveur gRPC Go et un `socketserver` Python tournent **sans modification**.
- **Les Workers reçoivent moins** : gRPC unaire et server-streaming uniquement, **pas de bidirectionnel** — le mécanisme est une traduction gRPC ↔ gRPC-web, pas un support natif.
- **La raison** : HTTP/2 découpe en frames porteuses d'identifiants de flux, et `fetch()` n'expose pas ce niveau. C'est exactement pourquoi gRPC-web existe pour les navigateurs.
- **Bêta privée assumée** : Cloudflare écrit ne pas utiliser gRPC en interne (Cap'n Proto et le RPC natif des Workers) et vouloir valider l'implémentation avant d'ouvrir.

Sa communication sociale annonçait « now available » et du gRPC natif sans couche de traduction — c'est plus étroit que ça.

## Top 3 — Uber GitFarm : Git comme service gRPC

- **Le coût qu'on ne voit plus** : cloner le monorepo Go d'Uber prend ~15 minutes, ~6 cœurs CPU, 32 Go de RAM et plus de 40 Go de disque. Multiplié par des millions d'invocations Git par jour.
- **Le principe** : GitFarm n'est **pas** un SCM. C'est un client Git centralisé qui exécute des commandes Git standard pour le compte d'autres services, derrière une API gRPC.
- **Le levier** : des pools de checkouts pré-chauffés et de sandboxes éphémères. Une requête monte un checkout existant au lieu de cloner — **moins d'une seconde**.
- **Sessions multi-commandes** : le streaming gRPC bidirectionnel enchaîne fetch, calcul de merge-base et push sur le **même** checkout sans réinitialiser l'état.
- **Chiffres de production** : un service de code ownership passe de 70+ cœurs à 16 et de 400 à 32 Go ; un service d'audit de conformité passe de 110-160 s à 20-30 s de latence médiane.

En production depuis début 2025. Roadmap : sparse checkouts, sessions longues, mirroring.
